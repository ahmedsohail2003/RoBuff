UB Hacking 2026 · Deep space

Pick up a space rock with your bare hand, by friction alone, if a lift test passes. with your bare hand.

Light takes 2.56 s to reach the Moon and back; in a 2024 University of Bristol study, people steering a robot arm at delays up to 2.6 s did worse on every measure. Robuff lets your webcam hand fly a simulated arm that grips by friction, and a ghost arm shows where it is headed. So far only a scripted hand has flown it: the cube rose 78.4 mm in 5 of 5 runs.

Your hand drives the arm

Refusals come with the numbers.

Generated objects are only useful if the arm can actually hold them, so every request is checked first, then placed in the scene and proven with a simulated lift test, and an object that fails the lift is taken back out. I tested seven requests end to end in the browser: five were lifted, one of them only after being rebuilt as a smaller model, and two were refused by the checks before they were placed.

Why these tools. Each one solves a problem plain code couldn't.

MuJoCo

Working

A robotics physics engine that simulates contact and friction. I run it in the browser so a rock rises only if friction really holds it.

MediaPipe Hand Landmarker

Working (real hand not tested yet)

Google's public hand-pose model: 21 points per hand from a camera image, on the laptop, so no frame is uploaded. Median 11 ms a frame on Chrome's fake camera (RTX 4050).

SO-ARM100 from MuJoCo Menagerie

Working

A small open-source arm (5 joints and a jaw) from MuJoCo Menagerie, a library of checked robot models. Used as published, nothing tuned.

Playwright and Vitest

Working

Playwright drives a real Chrome from a test script, so the scripted pick, the fake camera and the object requests can be re-run by anyone. Vitest, a JavaScript unit-test runner, runs the tests on the physics, filters and checks without a browser: 201 of 201 passed.

Gemini 3.8 Flash

Working (format check 5 / 5)

Google's large language model. It turns a free-text request into a structured spec (kind, size, material) that the checks can test; a small server holds the API key so it never reaches the page. Live test: 5 of 5 replies in the right format, median 3867 ms, but that gate checked the format only, and the sizes returned did not always match the request.

The ghost arm (a predictive display)

Built · result not measured

A second simulation runs your commands with no delay and draws a see-through arm where the real one is headed. ROTEX flew the idea in 1993. Helps a person? Not measured yet.

Voice runs offline: typed commands, and the browser's built-in voice speaks each reply with captions (tested in Chrome). ElevenLabs, a text-to-speech service, would give the console a natural voice; that route is written but untested, because no ElevenLabs API key is set up yet. Without a Gemini key, an offline parser reads requests instead, labelled on screen.

The app's hard limits for objects (10 to 70 mm wide, up to 300 g) were set with a safety margin from grasp tests on the simulated arm. For flying by hand the app keeps a margin inside them, 15 to 55 mm and 200 g, and those are the limits the calculator and the refusals use. A real SO-ARM100's payload is unverified.

Arm model: MuJoCo Menagerie SO-ARM100 (trs_so_arm100, Apache-2.0), from The Robot Studio's SO-ARM100. Physics: MuJoCo. Hand tracking: Google MediaPipe hand landmarker. Rendering: three.js. Gravity and distance data: NASA NSSDC fact sheets and JPL's small-body database. Predictive-display idea: MIT (Sheridan 1984) and JPL (Bejczy, Kim and Venema 1990), flown on DLR's ROTEX in 1993. Delay study: Louca et al. 2024, University of Bristol, ACM Transactions on Human-Robot Interaction, doi:10.1145/3651993. Page layout inspired by ZELT (zelt-nu.vercel.app).

Planned, coded and tested with Claude Code (Anthropic's Claude) under my direction and review. Inside the app, the MediaPipe hand landmarker runs in the browser, and Gemini 3.8 Flash reads typed object requests when a key is set on the key server.
